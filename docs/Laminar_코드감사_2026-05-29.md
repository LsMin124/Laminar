## 1. CRITICAL — 멀티테넌트 격리 필터가 프로덕션에서 미활성 (C-1)

### 1.1 설계 의도
Personal-First 격리는 Hibernate `@FilterDef`/`@Filter`로 구현됩니다.

- `context/package-info.java:10-19` — `@FilterDef(personalFirstFilter, ...)`, `@FilterDef(workspaceSharedFilter, ...)` 선언. **`autoEnabled` 미설정** → Hibernate가 자동 적용하지 않음.
- `card/CardEntity.java:23-24` — `@Filter(name="personalFirstFilter", condition="workspace_id = :ctxWorkspaceId and user_id = :ctxUserId")`. (Board/Tab/Group/Perpetual/DateMemo/Attachment/Equipment 등 다수 엔티티 동일 패턴)
- 활성화 책임은 `context/HibernateFilterActivator`:
  - `activate()` (`:35`) — 현재 Session에 `enableFilter` + 파라미터 바인딩.
  - `registerForCurrentTransaction()` (`:88`) — 트랜잭션 동기화에 등록 + 즉시 `activate()`. 주석상 "@Transactional 모든 메서드에서 자동 동작" 의도.

### 1.2 실제 (결함)
호출 그래프 추적 결과:

```
registerForCurrentTransaction()  →  호출처 0건 (정의만 존재, dead code)
activate()                       →  AdminWorkspaceService, RruleExpansionWorker, *그리고 테스트에서만*
```

- `WorkspaceContextRequestFilter`(`:45-80`)는 ThreadLocal `WorkspaceContext`만 설정하고 **필터를 활성화하지 않습니다** (`HibernateFilterActivator`를 주입조차 하지 않음).
- AOP(`@Aspect`/`@Around`), Hibernate `Integrator`/`StatementInspector`/`SessionFactoryObserver`, `BeanPostProcessor`, `@PostConstruct` 어디에도 활성화 훅이 없음(전수 grep 확인).
- 도메인 서비스(`CardService` 외)는 **수동 워크스페이스/유저 일치 검증이 전무**합니다. 수동 `.equals` 소유권 검증을 하는 클래스는 `AdminWorkspaceService`·`WorkspaceMemberService` 둘뿐.

예: `card/CardService.java`
```java
public Optional<CardEntity> findById(UUID cardId) {
    WorkspaceContextHolder.require();              // 컨텍스트 "존재"만 확인
    return cardRepo.findById(cardId)               // ← 필터 미활성, workspace/user 검증 없음
            .filter(c -> c.getDeletedAt() == null); // ← soft-delete만 거름
}
```
`listByBoard(boardId)`(`:91`), `update`(`:109`), `archive`(`:157`), `softDelete`(`:169`), `reorder`(`:136`) 모두 동일하게 `cardRepo.findById/findByBoardId...`만 호출 — 소유권 불문.

### 1.3 영향 / 악용 시나리오
- **전제**: 인증 사용자 1인(가입 시 본인 personal 워크스페이스의 OWNER 자동 생성 → 모든 사용자가 충족). 본인 워크스페이스 ID를 `X-Laminar-Workspace-Id`로 보내면 PERSONAL 컨텍스트 통과.
- **읽기**: `GET /api/cards/{uuid}`, `/api/cards/{uuid}/rendered`, `/api/boards/{uuid}`, `/api/attachments/{uuid}` 및 `/download-url` → **타 테넌트 리소스 반환**.
- **목록 증폭**: `GET /api/cards?...`(boardId 기준), `listByParent(parentType,parentId)` 등은 **타인의 board/parent UUID 하나만 알면 해당 하위 전체 행**을 반환 — 단일 UUID로 다수 노출.
- **쓰기/삭제**: `PUT/DELETE /api/cards/{uuid}`, reorder, archive → 타 테넌트 데이터 변조·삭제.
- **첨부 파일**: `/api/attachments/{uuid}/download-url`은 엔티티의 `storageKey`로 presigned GET URL 발급 → 깨진 `findById` 경유로 **타 테넌트 실제 파일 다운로드**.

**악용성 단서(공정한 평가)**: UUID는 `gen_random_uuid()`(122비트)라 순차 열거는 불가능합니다. 그러나 (a) 목록 엔드포인트가 parent UUID 하나로 하위 전체를 노출하고, (b) UUID는 공유 링크·관계 응답·운영 콘솔·로그·Referer 등으로 일상적으로 누출되며, (c) 같은 연구실 동료 간에는 ID 획득이 용이합니다. 즉 대량 스크래핑 난이도는 있으나 **제품의 격리 보증 자체가 런타임에서 완전히 무효**입니다 → CRITICAL.

### 1.4 권고 (택1 + 방어심화)
1. **즉시(요청 경로 활성화)**: `WorkspaceContextRequestFilter`가 컨텍스트 설정 후 트랜잭션 진입 시 필터를 켜도록 결선. 가장 견고한 방식은 `@Transactional` 경계에서 동작하는 AOP Aspect 또는 `TransactionSynchronizationManager` 훅이 `HibernateFilterActivator.activate()`를 호출하는 것. (현 `registerForCurrentTransaction`의 `beforeCommit` 콜백은 **읽기에는 무용** — 쿼리는 commit 전에 실행됨. `activate()`는 트랜잭션/Session 시작 시점에 호출돼야 함.)
   - 권장: `@FilterDef(autoEnabled = true)`로 전환 + 매 Session 시작 시 파라미터 바인딩(미바인딩 시 쿼리가 **실패**하도록 — fail-closed). 현재처럼 미활성 시 조용히 전체 노출되는 fail-open은 금물.
2. **방어 심화(필수)**: 도메인 서비스의 단건 조회/수정에 **명시적 소유권 검증** 추가 — `card.getWorkspaceId().equals(ctx.workspaceId()) && card.getUserId().equals(ctx.userId())` 불일치 시 404. ORM 필터 단일 의존은 위험(이번 사고가 증명). DB 레벨 **PostgreSQL Row-Level Security(RLS)**를 최종 방어선으로 추가 검토.
3. **회귀 방지**: 아래 L-2의 MockMvc 교차 테넌트 테스트를 CI 게이트로.

## 2. HIGH

### H-1 — 레이트리밋 전무
- `build.gradle.kts`에 `com.bucket4j:bucket4j-core:8.10.1` 포함되나 **코드에서 미사용**(전수 grep 0건). 전역 규칙("모든 엔드포인트 레이트리밋")과 위배.
- 노출 위험:
  - `POST /api/auth/login` — 무차별 대입·credential stuffing(BCrypt 12가 다소 완화하나 분산 공격엔 불충분).
  - `POST /api/auth/signup`, 초대 발송 — 가입/메일 발송 남용(Resend 비용·평판).
  - `POST /api/attachments/upload-url` — presigned URL 대량 발급.
- **권고**: bucket4j로 IP+계정 키 기반 로그인 슬라이딩 윈도(예: 5회/분, 지수 백오프), 가입·발신·presign 별도 버킷. 로그인 실패 누적 시 계정 일시 잠금(현재 `users`에 시도 카운트 컬럼 없음).

### H-2 — 전역 예외 핸들러 부재
- `@ControllerAdvice`/`@RestControllerAdvice`/`@ExceptionHandler`/`ResponseStatusException` **전무**(전수 grep 0건).
- 결과:
  - `AuthController.login`의 `IllegalArgumentException("invalid credentials")` → **HTTP 500** (401 아님).
  - `requirePersonalWritable()`의 `IllegalStateException("VIEWER cannot mutate")`, `WorkspaceContextRequestFilter`의 비멤버 → 서비스 단 예외는 **500**(403/409 아님).
  - `signup` 중복 시 `IllegalStateException("email already registered")` → 500(409 아님) + 동작 차이로 enumeration 보조.
- 영향: API 계약 붕괴, 클라이언트가 client/server 오류 구분 불가, Sentry에 가짜 500 폭주, 운영 가시성 저하. (Spring Boot 3 기본 `include-message:never`라 본문 메시지 누출은 없으나 상태코드가 전부 틀림.)
- **권고**: `@RestControllerAdvice`로 도메인 예외→상태코드 매핑(`IllegalArgument→400`, `invalid credentials→401`, scope/role→403, not found→404, 중복→409). 표준 에러 envelope(공통 규칙의 success/data/error 형식) 채택.

### H-3 — 의존성 버전 신뢰성 / 재현성
- `build.gradle.kts`·`package.json`의 다수 버전이 **미래 날짜·실재 불명**으로 보임: `owaspSanitizerVersion "20260313.1"`, `tika 3.3.0`, 프론트 `typescript ~6.0.2`, `vite ^8.0.12`, `react ^19.2.6`, `lucide-react ^1.16.0`(lucide-react는 0.x 대), `eslint ^10`, `@types/node ^24`. 작성 시점 레지스트리에 미존재 가능 → **의존성 해석 실패/비재현 빌드** 위험.
- `apps/web/package.json`에 `"@playwright/test": "^1.50.0"` **중복 키**(두 번 선언) — 무효 항목, 도구가 마지막 값만 채택.
- **권고**: 레지스트리(ground truth) 대조로 전 버전 검증·핀 고정, lockfile 재생성. Renovate/Dependabot + `gradle dependencyUpdates`/`pnpm outdated` 도입. Spring Boot 3.5.0은 패치 최신화 및 CVE 피드 대조.

### H-4 — 프론트엔드/백엔드 JSON 네이밍 불일치 (회원가입 프로덕션 차단)
- **증상 (2026-05-29 배포 후 보고)**: 회원가입 시 "입력값을 확인해주세요."만 표시되고 다음 단계로 진행 불가.
- **근인**: `application.yml:13` `spring.jackson.property-naming-strategy: SNAKE_CASE` → 백엔드는 요청을 snake_case(`display_name`)로 역직렬화. 그러나 프론트(`SignupPage.tsx:20` → `lib/api.ts`의 `JSON.stringify`)는 변환 없이 camelCase(`displayName`)로 전송 → 백엔드 `displayName=null` → `AuthDtos.SignupRequest`의 `@NotBlank` 실패 → **HTTP 400** → `SignupPage.tsx:23`이 `err.status===400`을 "입력값을 확인해주세요."로 매핑.
- **로그인은 통과한 이유**: 로그인 본문은 `email`/`password`로 단일 단어라 snake/camel이 동일. 배포로 FE/BE가 처음 함께 동작하면서 다단어 필드를 가진 회원가입에서만 표면화.
- **국소 버그 아님 (광범위·조용한 손상)**: 프론트 `types.ts`는 100% camelCase(snake_case 접근 0건), 백엔드엔 `@JsonProperty`/별도 ObjectMapper 없음 → `SNAKE_CASE` 한 줄이 유일한 불일치. 따라서 **응답**의 다단어 필드(`userId`·`workspaceId`·`startDate`·`bodyMd`·`defaultView` 등)도 현재 클라이언트에서 전부 `undefined`이며, 카드·보드 생성의 다단어 **요청** 필드도 누락됨.
- **권고 (택1)**:
  - (A·권장) `application.yml`에서 `property-naming-strategy: SNAKE_CASE` 제거 → 백엔드 기본 camelCase로 프론트와 정렬. 한 줄 수정으로 요청·응답 양방향 동시 해결. 재빌드·재배포 필요.
  - (B) 프론트 `api.ts`에 요청 직렬화/응답 역직렬화 case 변환 레이어 + 전 타입 snake_case화 — 변경 광범위, 비권장.
- **주의**: 수정·재배포 후에도 같은 메시지가 보이면 실제 입력 검증 위반(비밀번호 8자 미만 / 이메일 형식 / 표시이름 100자 초과)이며, H-2(전역 예외 핸들러 부재)로 모든 400이 동일 메시지로 뭉뚱그려진 결과. 가입 폼 필드별 메시지 권고.
- **상태**: **문서화만 (코드 미수정 — 사용자 요청).** 배포본은 위 수정·재배포 전까지 회원가입 차단이 지속됨.

## 3. MEDIUM

### M-1 — CSRF가 SameSite=Lax 단일 의존
- `SecurityConfig:45` `csrf disable`. 주석은 "SameSite=Lax + custom header 패턴"이라 하나 **custom header 검증은 미구현**(`SessionAuthenticationFilter`는 쿠키만 읽음).
- 실제 방어는 `AuthController:109`의 `SameSite=Lax`뿐. Lax는 교차 출처 POST를 막지만 (a) SameSite 미지원 구형 브라우저 무방비, (b) 방어심화 부재, (c) 향후 프론트를 별도 출처로 분리하면 쿠키가 cross-site가 되어 유일 방어가 붕괴.
- **권고**: 상태 변경 요청에 더블 서브밋 토큰 또는 필수 custom header(`X-Laminar-Workspace-Id`를 모든 변경 요청에 강제 — 교차 출처는 preflight로 차단) 검증을 명시 구현. 문서와 코드의 불일치 해소.

### M-2 — 세션 토큰 평문 저장
- `SessionService.generateToken()`(256bit SecureRandom) 결과를 그대로 `session_token`에 저장(`V2 sessions.session_token TEXT UNIQUE`). 쿠키 값 == DB 값.
- DB 유출(백업·리드레플리카·다른 인젝션·로그) 시 **활성 세션 전체 탈취** 가능.
- 같은 코드베이스가 `workspace_invitations.token_hash`는 SHA-256 해시 저장 — **일관성 결여**(세션도 동일 처리해야 함).
- **권고**: 쿠키엔 raw, DB엔 `SHA-256(token)` 저장 후 조회 시 해시 비교. 마이그레이션은 신규 세션부터 적용.

### M-3 — 사용자 enumeration
- `UserService.verifyCredentials`(`:49`)는 미존재 이메일이면 **BCrypt 비교 없이 즉시 반환** → 존재(느림)/미존재(빠름) **타이밍 차이**로 이메일 enumeration.
- `signup`(`:35`) 중복 시 예외 → (H-2와 결합) 동작/상태 차이로 가입 enumeration.
- **권고**: 미존재 시에도 더미 BCrypt 비교로 상수 시간화. 로그인/가입 응답은 일반화("이메일 또는 비밀번호가 올바르지 않습니다", 가입은 "확인 메일 발송" 일률).

### M-4 — 파일 업로드 검증 미흡
- `R2StorageService.createUploadUrl`(`:51`)은 클라이언트 `mime`을 그대로 content-type으로 서명 — **타입 allowlist 없음**. `Tika`(content-type 감지) 의존성은 있으나 **미사용**.
- presigned PUT에 **content-length-range 조건 미설정** → 무제한 크기 업로드 가능(R2 비용·스토리지 고갈). `AttachmentService`의 20MB 검증은 메타 단계에만 적용되어 실제 바이트를 막지 못함.
- 다운로드 시 `Content-Disposition: attachment` 미강제 → R2가 업로드 content-type대로 서빙 시 저장형 콘텐츠 악용 여지(별도 출처라 위험은 제한적이나 방어심화 필요).
- **권고**: 업로드 MIME allowlist(이미지/PDF 등), presigned PUT에 크기 상한 조건, finalize 시 Tika로 매직바이트 재검증, 다운로드 응답 헤더 강제.

### M-5 — `createDownloadUrl(storageKey)` 소유권 미검증
- `R2StorageService.createDownloadUrl`(`:61`)은 임의 `storageKey`를 받아 presigned URL 발급, **키 prefix(`workspaces/{ctx.workspaceId}/users/{ctx.userId}/`) 검증 없음**. `WorkspaceContextHolder.require()`로 컨텍스트 존재만 확인.
- 현재 컨트롤러는 엔티티의 키만 넘기지만, 그 `findById`가 C-1로 깨져 있어 결과적으로 교차 접근. **방어심화로 키 prefix 일치 검증을 추가**해야 C-1 수정 후에도 안전.

### M-6 — OAuth 토큰 암호화 미구현 / 데드 시크릿
- `GoogleOAuthTokenEntity`는 `access_token_enc`/`refresh_token_enc`(byte[]) + `key_version` 컬럼을 두나, **암호화 코드(Cipher/AES/GCM)·`APP_SECRET_V1` 사용처 전무**. `GoogleOAuthTokenRepository`·OAuth 콜백 컨트롤러도 부재 → **gcal 토큰 플로 미완성/고아**.
- `.env`의 `APP_SECRET_V1`, `CRON_SECRET`(HTTP cron 엔드포인트 없음 — `@Scheduled`+ShedLock 인프로세스), `SAMPLE_MANAGER_HMAC_SECRET`(HMAC 검증 미구현)은 **현재 미사용 데드 시크릿**.
- **권고**: gcal 완성 시 envelope 암호화(AES-GCM + `APP_SECRET_V1`, `key_version` 회전) 실제 구현. 미사용 시크릿은 제거하거나 구현 전까지 발급 보류(시크릿 표면 최소화). 외부 sample-manager 연동 엔드포인트의 인증(HMAC 서명 검증) 부재 여부 점검.

### M-7 — 운영 콘솔 scope 전환의 비대칭 `activate()`
- `AdminWorkspaceService`(`:53-62`)는 SYSTEM scope 진입 후 `filterActivator.activate()`로 "Personal-First 필터 회피"를 의도하나, `activate()`는 **필터를 enable만 할 뿐 disable하지 않음**(SYSTEM scope면 early-return). 즉 한 번 켜진 필터를 끄지 못함.
- 현재는 C-1로 필터가 애초에 안 켜져서 우연히 동작. **C-1 수정으로 요청 경로가 필터를 켜는 순간, 운영 콘솔의 SYSTEM 전환이 깨짐**(이전 personal 파라미터로 계속 필터링). 수동 `.equals` workspace 검증이 있어 데이터 노출은 막히나 기능 회귀.
- **권고**: `HibernateFilterActivator`에 `disable()` 추가, scope 전환 시 명시적 enable/disable. C-1 수정과 동시 처리.

### M-8 — 낙관적 락 부재
- 엔티티에 `@Version` 없음. `CardService.update`/`reorder`, perpetual 버전 등 동시 편집 시 **갱신 유실(lost update)**. 협업 워크스페이스 특성상 현실적 위험.
- **권고**: 변경 빈번 엔티티에 `@Version` 추가, 충돌 시 409.

### M-9 — 이메일 검증 미강제
- `emailVerifiedAt` 컬럼·응답 필드는 있으나 `login`은 검증 여부와 무관하게 세션 발급. 검증 토큰 발송은 "Phase 4.5"로 연기되어 미구현.
- (H-1 무레이트리밋과 결합) 미인증 대량 가입·스팸 가능. 제품 요구에 따라 결정하되, 최소한 발신/초대 기능은 검증 게이트 권고.

## 5. 잘 된 점 (유지·확산할 패턴)

- **SQL 인젝션 표면 없음** — 전 쿼리가 JPA 파생 쿼리/`:param` JPQL. 문자열 결합 쿼리 0건.

- `.env`는 `.gitignore`로 미추적(실제 git 추적 안 됨 확인). soft-delete + audit_log + ShedLock 분산 락.
- **ArchUnit** 아키텍처 테스트로 계층/EntityManager 사용 규율. 격리 *설계* 자체(컨텍스트 3계층 + 필터)는 건전 — 결함은 *결선* 누락.

## 7. 수정 적용 현황 (2026-05-29, 배포·검증)

**해결 (구현 + 배포)**
- **C-1** ✅ 격리 결선 + 전 서비스 소유권 검증 + 회귀 IT (라이브 검증 통과).
- **L-2** ✅ `CrossTenantIsolationIT` 추가.
- **H-2** ✅ `GlobalExceptionHandler`(@RestControllerAdvice) + 표준 envelope. IllegalArgument→400, IllegalState→403(권한 관례), 검증→400, OptimisticLock→409, DataIntegrity→409, 로그인 실패→401(ResponseStatusException), 그 외→500(일반화).
- **H-1** ✅ `RateLimitFilter`(bucket4j) — login 10/분, signup 5/분, upload-url 30/분, invitations 20/분, IP(X-Forwarded-For) 기준, 429+Retry-After. 인스턴스별 인메모리(다중 머신은 머신당).
- **M-2** ✅ 세션 토큰 SHA-256 저장 — 쿠키 raw, DB 해시. 필터 조회 시 해시 비교(`SessionService.hashToken`).
- **M-3** ✅ 상수시간 자격검증 — 미존재 사용자도 디코이 BCrypt 비교 + 로그인 응답 일반화(401).
- **M-4** ✅ 업로드 MIME allowlist(스크립트형 html/svg/js 제외) + 다운로드 `Content-Disposition: attachment`. M-5(키 prefix)는 C-1에서 완료.
- **M-8** ✅ 낙관적 락 — `boards/cards/perpetual_notes`에 `@Version`+`version` 컬럼(V13), 충돌 409.

**미적용 (근거)**
- **M-1** CSRF: 현재 `SameSite=Lax` + JSON Content-Type(교차출처 preflight 차단)로 단일 출처에선 baseline 방어. 더블서브밋/custom-header 강제는 프론트 전반 수정 동반·회귀 위험 → 별도 작업. 프론트를 별도 출처로 분리할 때 필수.
- **M-6** OAuth 암호화/데드 시크릿: gcal 토큰 플로 자체가 미구현(Repository/콜백 부재)이라 암호화할 대상 없음. 시크릿은 Fly secret(인프라)이라 코드에서 정리 불가 — gcal 구현 시 envelope 암호화 동반.
- **M-9** 이메일 검증 강제: 검증 메일 발송이 미구현 → 강제 시 전 사용자 로그인 차단. 발송 파이프라인 구축 후 게이트.
- **L-1** `forward-headers: native`: Fly 엣지로만 도달 가능한 인프라 전제가 충족되어야 안전 — 코드 아닌 네트워크 정책 사안.
- **RLS**(P2): ORM 필터 + 서비스 소유권 검증 + 회귀 IT로 다층 방어 확보. RLS는 대규모 마이그레이션 동반 — 최종 방어선으로 추후 도입.
- **H-3**(빌드 재현성): 원격 Docker 빌드가 전 의존성 해석·컴파일·bootJar 성공으로 "버전 실재 불명" 우려 해소(경험적). `package.json` 중복 키 제거·lockfile 동기화 완료. **별건**: `spotlessCheck`가 전 저장소에서 실패(코드가 spotless 미포맷 — 들여쓰기·줄바꿈) → `./gradlew build`의 `check`가 기존부터 red. 배포는 Dockerfile이 `-x spotlessCheck`라 무관. 정합하려면 1회 repo-wide `spotlessApply`가 필요하나 보안 수정과 분리 권장(205+ 파일 churn).
