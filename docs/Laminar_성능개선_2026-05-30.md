# Laminar 성능 개선 기록 (2026-05-30)

> 페이지 로드 지연 진단 → VM 자원 상향(적용 완료) → 잔여 최적화 레버 정리.
> 측정은 sandbox→Fly(nrt) 경로 기준이라 **네트워크 바닥값 ~0.45s가 포함**된 절대치이며,
> 항목 간 **상대 비교**가 신뢰 가능한 신호다.

## 1. 증상

- 사용자 보고: "페이지 로드가 상당히 느리다."
- 실측(상향 전): index.html / JS 번들 / 모든 API가 **30s 타임아웃**. `/actuator/health` 8.4s.
  두 머신 모두 `critical`.

## 2. 근본 원인 (크래시 아님 — 순수 자원 기아)

- VM `shared-cpu-1x` / `512MB`에서 CPU 기아.
  로그: `Root WebApplicationContext: initialization completed in 89041 ms` (정상은 ~10s).
- 부팅 89초 동안 health check(`timeout=5s`)가 계속 실패 → **passing↔critical 플래핑** →
  Fly가 비정상으로 보고 **재시작 루프**. 그 결과 요청이 30s 타임아웃.

## 3. 적용한 수정 (commit `da9528f`, 배포·실측 완료)

`fly.toml`:

| 항목 | 이전 | 이후 |
|---|---|---|
| VM size | `shared-cpu-1x` | `performance-1x` (전용 CPU) |
| memory | `512mb` | `2048mb` |
| health `timeout` | `5s` | `10s` |
| health `grace_period` | `15s` | `120s` (cold start 플래핑 방지) |
| 머신 수 | 2 | 1 (`fly scale count 1`, 연구실 내부용 HA 불필요) |

### 결과 (상향 후 실측)

| 경로 | 이전 | 이후 |
|---|---|---|
| 부팅(green까지) | 89s, 플래핑 | **~1s** |
| index.html (DB 없음) | 30s timeout | **0.48s** |
| JS 번들 (626KB) | timeout | **0.81s** |
| `/api/auth/me` | timeout | **0.33–0.89s** |
| `/api/workspaces` | timeout | **0.76s** |
| `/api/boards` | timeout | **0.76s** |

VM 상향으로 **다운 상태는 해결**. 이하 잔여 레버는 "modern fast UX"를 위한 추가 최적화.

## 4. 잔여 최적화 레버 (영향 큰 순 — 미적용)

### L-P1. 부트스트랩 워터폴 제거 ★ 최우선 (체감 속도 지배)

- 현재 SPA 콜드 스타트가 **직렬 4회**:
  `GET /api/auth/me` → (신규 사용자만) `GET /api/workspaces` → `GET /api/workspaces/current` → `GET /api/boards`.
  네트워크 바닥값 0.45s × 4 + DB ⇒ 보드 렌더까지 **~3.2s**.
- `App.tsx`의 `me.isLoading` 게이트가 **전체 앱 렌더를 차단**(me 완료 전 아무것도 안 그림).
- `BoardsPage.tsx`가 `useCurrentWorkspace(true)` + `useBoards(true)`를 **둘 다** 호출 →
  `/workspaces/current`는 **리던던트**(워크스페이스 정보는 부트스트랩 `/workspaces` 목록에 이미 존재).
- **개선안 (택1)**:
  - (간단) 리던던트 `/current` 제거 + 독립 호출(`me`, `boards`) 병렬화·prefetch.
    예상: ~3.2s → ~1.6s.
  - (근본) 통합 엔드포인트 `GET /api/bootstrap` → `{user, workspaces, currentWorkspace, boards}` 1회.
    리전 co-location(L-P2)과 결합 시 ~0.5s. **권장**.

### L-P2. DB 리전 co-location (Fly nrt → sin) ★ 쿼리당 ~75ms

- 현재: Fly `nrt`(도쿄) ↔ Neon `ap-southeast-1`(**싱가포르**). 매 쿼리 **교차리전 ~80ms RTT**.
  인증 API 1회는 세션+멤버+데이터 = 쿼리 1~3회 ⇒ DB만 80~240ms.
- Fly를 `sin`(싱가포르)로 옮겨 Neon과 co-locate → 쿼리당 **~5ms** (≈75ms/쿼리 절감).
- **트레이드오프**: 한국 사용자→앱 정적 응답 +~40ms(1회성, CDN/캐시로 흡수 가능).
  DB 중심 SPA에서는 순이득(매 상호작용 ~200ms↓ vs 정적 1회 +40ms).
- ⚠️ **`fly.toml` line 6 주석 오류**: "nrt — Neon ap-southeast-1과 가장 가까움"은 **틀림**.
  싱가포르(`ap-southeast-1`)에 가장 가까운 Fly 리전은 `sin`이다.
- **주의(결정 필요)**: 프로덕션 리전 이전 = 머신 재생성(짧은 다운타임) + 데이터 처리 지리 변경.
  사용자 승인 후 진행 권장(되돌리기 가능, 리스크 낮음).

### L-P3. 프론트 코드 분할 ★ TTI/파싱

- 단일 번들 **626KB / gzip 194KB** (Landing 예산 150KB 초과 — `web/performance.md` 기준).
- 라우트 lazy-load 대상: `BoardDetailPage`, `CardDetailPage`, `PerpetualPage`,
  `EquipmentPage`, `EquipmentDetailPage`, `AdminPage`, `MembersPage`.
  초기 번들에는 로그인 + BoardsPage만 → 첫 페인트/TTI 단축.

### L-P4. 인증 경로 쿼리 캐싱 (선택, 보류)

- 세션·멤버십이 매 요청 조회. 짧은 TTL 인메모리 캐시(Caffeine)로 요청당 1~2 쿼리 제거 가능.
- **보류 사유**: 멤버십 revocation 즉시성과 트레이드오프. L-P1/L-P2 적용 후 재평가.

## 5. 권장 적용 순서

1. **L-P1** (무위험, 프론트만) — 체감 속도 최대.
2. **L-P3** (무위험, 프론트만) — 초기 로드 경량화.
3. **L-P2** (사용자 승인 후) — 지속 API 지연 구조적 절감.
4. **L-P4** (L-P1/2 후 필요 시).

> L-P1·L-P3은 무위험이므로 감사문서 잔여 항목 처리 후 또는 별도 요청 시 즉시 착수 가능.
> L-P2는 프로덕션 인프라 결정이라 사용자 승인 필요.
